# Архитектура модуля «План-факт»

## Назначение

`План-факт` — единое рабочее пространство, которое объединяет три источника данных ПТО (`План`, `Опер учет`, `Марк замер`) и производные отчетные представления (`ААМ`, `АА`, `ААЕ` и пользовательские копии отчетов).

Модуль не должен дублировать данные между техническими вкладками. Отчеты являются вычисляемыми представлениями поверх источников ПТО и настроек отчета.

## Границы модулей

- `features/plan-fact` — навигация рабочего пространства, режим редактирования и управление отчетными вкладками.
- `features/pto` — ввод, редактирование, импорт/экспорт и хранение исходных данных План/Опер учет/Марк замер.
- `features/reports` — построение и отображение отчетов.
- `lib/domain/plan-fact` — чистые правила рабочего пространства без React и без доступа к хранилищу.
- `lib/domain/reports` и `lib/domain/pto` — расчеты и модели соответствующих предметных областей.
- `features/app` только компонует модули и не содержит бизнес-правила План-факта.

## Источники истины

### План

`План` — единственный источник плановых суточных значений. Месячные и накопительные значения рассчитываются из суточного плана и не требуют технических вкладок вида `График` или `ПланС`.

### Опер учет

`Опер учет` хранит полный ежедневный фактический учет. Исторические значения не удаляются и не перезаписываются при появлении маркшейдерского замера.

### Марк замер

`Марк замер` — более приоритетный источник факта для закрытого замером периода. Период замера не имеет фиксированной продолжительности: 5, 6, 7, 14 и любое другое количество дней должны обрабатываться одной и той же моделью.

Правило итогового факта:

1. Для части периода, закрытой маркшейдерским замером, используется маркзамер.
2. Для части периода, которая не закрыта замером, используется Опер учет.
3. Опер учет при этом сохраняется полностью как первичный ежедневный журнал.
4. Перекрывающиеся источники нельзя суммировать дважды.
5. Нулевой маркзамер является валидным значением и также имеет приоритет над Опер учетом.

## Отчеты

ААМ, АА, ААЕ и пользовательские отчетные вкладки используют одну расчетную модель. Различия между отчетами задаются конфигурацией `ReportCustomerConfig`, а не копированием расчетного кода.

Конфигурация отчетных вкладок сохраняется существующим механизмом shared persistence. В нее входят состав строк, скрытые строки, подписи, источники факта, итоговые строки, порядок участков и видов работ. Порядок самих отчетных вкладок определяется порядком `reportCustomers`.

Системные вкладки ААМ/АА/ААЕ можно переименовать и скрыть, но нельзя удалить. Пользовательскую вкладку можно создать из системного шаблона, переименовать, переместить, скрыть и удалить.

## Режим редактирования

Состояние режима редактирования принадлежит `features/plan-fact`, а не отчетам. При переходе между План/Опер учет/Марк замер и отчетами контроллер синхронизирует режим редактирования с редактированием таблиц ПТО и не оставляет скрытое активное редактирование после перехода в отчет.

Локальная кнопка редактирования таблиц ПТО остается совместимой: при ее изменении workspace синхронизирует свое состояние с `ptoDateEditing`.

## UI и расширяемость

Управление вкладками выполняется обычными контролами интерфейса, без `window.prompt`. Это позволяет добавить в дальнейшем права доступа, подтверждения, аудит и серверную валидацию без переделки навигации.

Следующий уровень расширения макета отчетов должен строиться через явную схему групп и колонок. Нельзя добавлять произвольный порядок столбцов простым переставлением DOM-элементов, потому что отчет имеет двухуровневые групповые заголовки (сутки, месяц, год, годовой план). Схема макета должна сохранять семантику групп, печать A3 и расчетные ключи колонок.

## Проверка перед production

Изменения План-факта должны проходить как минимум:

- ESLint;
- TypeScript typecheck;
- production build Next.js;
- domain checks расчетов ПТО/отчетов;
- архитектурные source checks приложения;
- production smoke после выкладки.

Новые возможности не считаются выложенными, пока workflow Deploy не прошел до шага production smoke.
